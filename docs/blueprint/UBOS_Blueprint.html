1. Executive Summary

UBOS is a multi-tenant SaaS product. You (the Platform Owner) run UBOS as a software business: other companies buy a subscription, get their own private, isolated workspace (a tenant), and run their whole business on it. Your own company is simply Tenant #1 — you use exactly the same product your customers buy, and you manage all customer companies, plans, billing, usage and support from one Platform Console.

Inside each tenant, UBOS is a single, web-based (and later mobile) portal that every team in that company logs into. It combines what is today spread across a tele-CRM, a WhatsApp tool, a cloud-calling dashboard, Google Sheets, an HR tool, spreadsheets for assets/incentives, and an accounting package. Every feature is exposed through a documented REST API, so the web app, a future mobile app, partner systems and AI agents all use the same rules.

What makes UBOS different from a plain CRM

One customer, one record

Duplicate detection on mobile/email/PAN merges every enquiry, call, chat, package, payment and document into a single Customer 360° timeline.

Sticky RM ownership

A Primary RM owns the customer permanently; Secondary RMs own individual packages — with shared notes and separate incentives.

Integrations you switch on/off

WhatsApp, CallerDesk, Google Sheets, Razorpay, Facebook, IndiaMart, JustDial and more live in an Integrations Hub. You activate, configure or deactivate each one yourself.

People + money in the same system

HRMS (onboarding to exit), assets, payslips, ledgers, collections and the incentive engine all read the same lead/package data — no re-keying.

Flexible, multi-role access

Create any role you need, assign several roles to one person, and control data scope, field visibility and CSV export per role.

Built to be sold

Plans, licences, module entitlements, usage metering, subscription billing, trials, white-label domains and tenant support — so UBOS earns recurring revenue for you.

You use it too

Your own business runs as Tenant #1, which makes your company the first reference customer and the live test bed for every release.

AI built in, provider of your choice

Gemini, Claude or OpenAI for chatbots, call summaries, lead scoring, message templates, ad copy, images and short-video scripts.

4. Platform Console, Tenants & Workspaces

UBOS has three levels. The Platform level is used only by you and your platform team to manage the software business. The Tenant (Organization) level is each customer company (and your own company). Inside an organization, Workspaces separate its business lines. A tenant can never see another tenant's data or the Platform Console.

Organization → Workspaces (business lines)

One tenant (organization) can create multiple workspaces, one for each business line, division, brand or process. Leads, pipelines, packages, teams, WhatsApp numbers and reports are kept separate per workspace, while the organization keeps one shared Customer Master. This lets the same customer be served (and cross-sold) by several business lines without duplicate records.

  • Pipelines inside a workspace: each workspace can also have several pipelines/processes, e.g. Education → Admissions, Renewals; Vastu → Consultation, Site Audit
  • Lead routing to workspaces: each source, form, WhatsApp number, CallerDesk number or webhook is mapped to a workspace (and pipeline); unmapped leads go to an "Unsorted" inbox for a manager to classify
  • Cross-sell: an RM can refer a customer from one workspace to another (e.g. a Course customer interested in Logo Designing); a new lead is created in the target workspace, linked to the same customer, with referral credit for incentives
  • Users in several workspaces: a user can work in one or many workspaces, with different roles in each (e.g. Manager in Vastu, RM in Logo Designing); a workspace switcher sits at the top of the screen
  • Workspace templates: create a new workspace from an industry template (Education, Real Estate, Consulting, Design Services, Software…) or by cloning an existing workspace

Plan enforcement (how selling actually controls the product)

  • Every API request carries the tenant; the API checks the tenant's plan entitlements before the user's role permissions. A module not in the plan is hidden in the menu and blocked in the API, with an "Upgrade" prompt for the tenant admin
  • User licence limit enforced when inviting users; usage quotas (storage, AI credits, API calls) enforced with warnings at 80% and 100%
  • Tenant admins see a Billing & Subscription page: current plan, licences, usage, invoices, upgrade, add licences, payment method

Integrations in a multi-tenant product

  • Each tenant activates and deactivates its own integrations with its own credentials (its own CallerDesk account, WhatsApp number, Razorpay, Google account, AI keys) — "bring your own account"
  • Optionally, you provide platform-managed services (e.g. AI credits, WhatsApp via your Tech Provider set-up) and bill usage with a margin
  • You as Platform Owner decide which integrations are available on which plan; tenant admins decide which ones they switch on

18. Roles & Permission Model (multi-role)

Permissions are checked in three layers: 1. Tenant (the request can only touch that tenant's data) → 2. Plan entitlement (is the module in the tenant's plan?) → 3. User roles (does any of the user's roles allow this action on this record?). Platform roles (Section 4) are a separate set and never mix with tenant roles.

Building blocks

ConceptDefinition
Permissionmodule.resource.action e.g. crm.lead.view, crm.lead.export, finance.refund.approve, hr.payslip.view
Data scopeAttached to each granted permission: Own < Team < Department < Branch < Workspace < Organization (all workspaces)
Field rulePer sensitive field: hidden / masked / visible / editable (e.g. mobile masked for Marketing)
RoleNamed bundle of permissions + scopes + field rules. Admins can create any number of roles
Permission templateStarting point to create a role (Root, Admin, Manager, Caller, Marketing, Finance, HR, Auditor…)
User ↔ RoleMany-to-many. One user can hold several roles, each assigned for a specific workspace or the whole organization, optionally limited to a branch/department and a validity period (e.g. "acting manager" for 30 days)

How multiple roles combine

  1. Union of permissions: if any role grants an action, the user has it
  2. Widest scope wins per permission (Team from one role + All from another = All)
  3. Most permissive field rule wins, except fields marked "restricted" which need an explicit grant
  4. Explicit deny (optional, used sparingly) overrides any grant — e.g. Auditor role denies all edit actions
  5. Segregation of duties checks: the system warns/blocks conflicting combinations (e.g. the same person cannot both create and approve a refund or incentive)

ConfigurationPlan entitlements + per-tenant feature flags + tenant settings (fields, stages, roles, branding)
UpgradesOne codebase for all tenants; schema migrations are backward-compatible and run once for the shared database, then per dedicated database

Key architecture decisions

  • Modular monolith first: one deployable backend with strict module boundaries. Modules talk via internal interfaces and events, so heavy ones (Telephony, Messaging, AI) can be split into separate services later without rewrites.
  • API-first: the web app has no private backdoor; it uses the same public REST API as the mobile app and partners.
  • Event-driven side effects: saving a record emits a domain event (e.g. lead.stage_changed); workflows, notifications, audit, webhooks and AI react asynchronously.
  • Multi-tenant from day one: every request is resolved to a tenant (from subdomain / custom domain and the JWT), every table carries tenant_id, and PostgreSQL row-level security blocks cross-tenant reads even if application code has a bug.
  • Separate Platform Console: a distinct app and API namespace (/platform/v1) for the Platform Owner, with its own roles and audit log.

23. API Design (API-first)

Conventions

  • REST + JSON at /api/v1/...; OpenAPI 3 spec auto-generated and published to an internal developer portal
  • Auth: Authorization: Bearer <JWT> for users; X-API-Key for apps; every request is permission- and scope-checked server-side
  • Cursor pagination (?limit=50&cursor=…), filtering (?filter[stage]=won), sorting, sparse fields
  • Idempotency keys on create/payment endpoints; standard error format { code, message, details, traceId }
  • Rate limits per user, per API key and per tenant; webhooks signed with HMAC-SHA256
  • Tenant is resolved from the host name and JWT on every call; the Platform Console uses a separate namespace /platform/v1 that tenant tokens can never call
