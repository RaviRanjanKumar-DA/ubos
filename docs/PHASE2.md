# Phase 2 — Calling, messaging, automation

Built in slices like Phase 1; each ends with end-to-end tests, a browser check, docs and a local commit. Everything is
tested locally first (no paid services until the product is complete); provider adapters are tested against local stand-ins
until a real account is connected.

| Slice | Scope | Status |
|---|---|---|
| 2.1 Calling core | One call pipeline for every channel: `Call` records (SIM, cloud, manual) with a stable id per organization (sent twice = stored once), call on the lead's journey at the time it happened, unknown numbers (optional new lead or "unmatched" to link later). Phone pairing (6-digit code → device token, revoke), mobile API (calls batch, reconcile, resumable recording upload, sync of my leads / follow-ups / dispositions, dial requests). Recordings encrypted at rest (local disk now, S3 / MinIO later), retention by plan / organization, listening permission and audit. Cloud calling: CallerDesk webhook → same pipeline, recordings copied or linked per setting, click-to-call. "Call" on a lead (paired phone or cloud). Live updates in open browsers (server-sent events). Calls page (log, filters, player, unmatched), phones admin, my phone. Built: `Call` / `Device` / `PairingCode` / `DialRequest`, mobile API `/mobile/v1` (pair, sync, calls, calls/reconcile, recording upload, heartbeat), CallerDesk webhook + click-to-call (field names and the click-to-call address follow CallerDesk's usual API — check against a real account), recordings encrypted on local disk (`STORAGE_DIR`), hourly retention purge, `crm.call.recording` permission, unknown-caller and "outcome required" settings, live updates via `/api/v1/stream`. | **Done** (34 e2e checks) |
| 2.2 SIM-calling Android app | Kotlin app in `apps/android`, per `design/SIM-CALLING.md`: pairing with a 6-digit code (token in the Android Keystore), today's follow-ups and all leads, tap to call with the SIM, call log capture for known leads only (personal calls stay on the phone), outcome screen with remark and next follow-up, offline queue and 48-hour reconciliation, recording upload in pieces, calls requested from the website while the app is open, IST throughout. Tested on the Android 37 emulator against the test server; real phones and real SIM calls, and each phone maker's own recording folders, are not yet checked. | Done (emulator) |
| 2.3 WhatsApp | WhatsApp Cloud API (Meta's free test number): shared inbox per business line, new chats → leads, templates, broadcasts with opt-out, chat on the lead. Built: signed Meta webhook (verify token, app secret), one copy per message id, new numbers become leads, chats follow lead scope, 24-hour rule, delivery ticks, STOP / START, registered templates with placeholders from lead fields, broadcasts from the Leads page, Inbox page, WhatsApp tab on the lead, live updates. Tested against a local stand-in for Meta — try the free Meta test number before relying on it. | **Done** (23 e2e checks) |
| 2.4 SMS & templates | DLT SMS provider adapter, message templates (WhatsApp / SMS / email) with lead placeholders. Built: SMS through MSG91 or any gateway by URL pattern (DLT template and entity IDs), delivery reports, email through the organization SMTP with an unsubscribe link, SMS / email templates, send from the lead, bulk send from the Leads page, opt-outs. Field names of delivery reports differ per gateway — check against a real account. | **Done** (20 e2e checks) |
| 2.5 Automation | Rules "when X, if Y, then Z" (assign, change stage, create task, send message, webhook), schedules, sequences that stop on reply. Built: Automation page with a rule builder, 11 triggers (new lead, stage change, won / lost, call logged, WhatsApp received, payment, quote accepted, process completed, no activity for N days), conditions, 9 actions (assign, change stage or status, label, task, remark, send template, notify owner, start a sequence), loop protection (at most 3 rules in a chain), run history, and multi-step WhatsApp / SMS / email sequences that stop when the customer replies. Outgoing webhooks stay in the Developer page. All dates in UBOS are now IST, whatever clock the server or device runs on. | **Done** (21 e2e checks) |
| 2.6 Calling campaigns | Power dialer queue with required disposition, campaign reports, call coaching comments on recordings. Built: Call campaigns page, list builder with live count, one-lead-at-a-time dialer, retries, pause, release of open calls, report by caller and outcome, CSV in IST, comments tied to a moment in the recording. A campaign never widens access: callers get only leads they can already work on. | Done (59 e2e checks) |
| 2.7 Help desk | Tickets linked to Customer 360, SLA, knowledge base. Built: Tickets page with queues and live counts, replies emailed to the customer, internal notes, first response and resolution targets per priority, clock stopped while waiting on the customer, past-target alerts, knowledge base with drafts and insert-into-reply. Clocks run 24x7. Customer-facing help pages come later. | Done (54 e2e checks) |
| 2.8 Connected accounts | Meeting booking links (IST hours, public page, double-booking guard, cancel link, lead and calendar meeting per booking). Native Facebook Lead Ads (connect pages, route pages and forms to business lines, signed webhook, resend on failure). Gmail / Outlook sync limited to customers the owner can see, one-to-one send, open and click tracking. Setup: `docs/CONNECTED_ACCOUNTS.md`. Real Facebook, Google and Microsoft accounts not yet checked. | Done (93 e2e checks against a local stand-in) |
| 2.9 Lead routing and scoring | Routing rules by city, source or any field (ordered, in turn among people, respects Sticky RM and people who are away). Scoring rules with a per-lead breakdown and recalculate. Moving a lead to another business line with a reason. 99acres, MagicBricks, Housing and Sulekha through a webhook with field mapping; portals that only send email or files use bulk upload or Google Sheets. Score from calls and email opens is not included yet. | Done (50 e2e checks) |
| 2.10 Chatbot and live chat | WhatsApp and website flows with buttons and questions, saving answers to the lead, handing to a person; a person replying stops the bot. Scheduling a template for one lead. Website chat button answered from the Inbox. Scheduling a whole broadcast, and the Instagram and Messenger inbox (needs its own Meta approval), are not built yet. | Done (51 e2e checks against a local stand-in) |
